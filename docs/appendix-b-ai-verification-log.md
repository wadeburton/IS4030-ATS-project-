## AI Reflection (team)

Generative AI — specifically Claude Code — was used throughout this project's data engineering and dashboard work: writing and testing the Flask/SQL dashboard code, writing and executing the SQL that loads the Gold star schema, and helping audit our own project documentation for requirements we had already committed to. Its biggest strength was speed on well-specified, mechanical work: generating SQL for the dimensional load, writing unit tests alongside each change (we required test-driven development, and the AI wrote the failing test first and then the minimal code to pass it every time), and producing a working UI revision in far less time than doing it by hand.

Its biggest risk showed up exactly where the request was easy to state but wrong to do literally. When we asked for "20 jobs to choose from," the AI's first useful move wasn't writing code — it was checking whether that request was even compatible with the system. It found that our own pipeline enforces a hard 2–3 job cap as a blocking quality gate, and that our own README and GitHub issues had already locked the study to that scope months earlier. Had we — or the AI — just done what was asked without checking, every future scan would have silently started failing, and our "final" study would have contradicted what we already told the instructor in Deliverable 1 and 2. The same pattern showed up with "add real jobs from GitHub": the AI didn't invent a plausible-sounding job posting, which would have been the actual hallucination risk here; it found the real additional data already sitting in our Bronze layer and reused our own prior sampling method to pick the next one, so the result is still something we can defend.

A second risk was the AI **assuming** a change had taken effect without checking the live system. After adding job-description text to the server code, the live dashboard still showed no description — the AI had restarted one running server process but not the other, running stale code under a URL we were actively looking at. The fix wasn't a code fix; it was a reminder that a deployed system's actual running state has to be checked directly (we re-queried the live Databricks tables and the live HTTP endpoints every time, not just the source files) rather than inferred from "the code now says X."

The verification habit we settled on across all of this: never trust a claim about data or configuration — ours or the AI's — without querying the actual system it describes. Every schema change was followed by running the project's own pre-written integrity SQL against the real warehouse, not just trusting that the load "should have worked." Every scope decision was checked against our own written deliverables rather than decided in the moment. That discipline is what turned several plausible-looking but wrong defaults (more jobs than the design allows, a shared embedded credential, a stale deployment) into caught mistakes instead of shipped ones.
